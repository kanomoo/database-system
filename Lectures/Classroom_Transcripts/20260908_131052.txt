คุณสมบัติ ACID Properties ของฐานข้อมูลเชิงสัมพันธ์ (Relational Database)
--------------------------------------------------------------------------------
ฐานข้อมูลที่ดีต้องมีคุณสมบัติ 4 ประการนี้เสมอ เรียกว่า ACID Property:

1. A - Atomicity (ความเป็นหนึ่งเดียว / แบ่งแยกไม่ได้):
   Transaction ต้องทำสำเร็จครบทั้งหมด (All) หรือไม่ทำเลย (Nothing) จะทำครึ่งๆ กลางๆ ไม่ได้เด็ดขาด ถ้าสำเร็จต้องจบด้วย COMMIT ถ้าพังต้องจบด้วย ROLLBACK คืนค่าเดิม

2. C - Consistency (ความถูกต้องสอดคล้อง):
   ข้อมูลก่อนเริ่มและหลังจบ Transaction ต้องมีความถูกต้องตามกฎเกณฑ์ (Integrity Constraints) เสมอ
   ตัวอย่างเช่น ผลรวมของเงินในระบบก่อนโอนและหลังโอนต้องเท่าเดิม
   หรือการถอนเงินจากตู้ ATM: เมื่อคุณกดถอนเงิน 1,000 บาท ระบบต้องตัดยอดเงินในบัญชีคุณ 1,000 บาท และต้องไปบันทึกในบัญชีรายจ่ายของธนาคาร 1,000 บาทเท่ากัน และบันทึกในตู้ ATM ว่าเงินสดในตู้ลดลง 1,000 บาท ทุกตารางต้องสอดคล้องตรงกันทั้งหมด

3. I - Isolation (การแยกตัวโดดเดี่ยว):
   ในระบบจริง มีผู้ใช้งานทำธุรกรรมพร้อมกันเป็นล้านคน เช่น คนถอนเงินตู้ ATM ที่กรุงเทพฯ และอีกคนถอนเงินที่เชียงใหม่ ระบบต้องแยกการทำงานของแต่ละ Transaction ไม่ให้มีผลกระทบถึงกัน ข้อมูลระหว่างทางที่ Transaction หนึ่งยังแก้ไขไม่เสร็จ (ยังไม่ COMMIT) Transaction อื่นจะต้องมองไม่เห็น เพื่อป้องกันไม่ให้อ่านข้อมูลที่ผิดพลาด

4. D - Durability (ความคงทนถาวร):
   เมื่อ Transaction ได้รับการยืนยันด้วยคำสั่ง COMMIT เรียบร้อยแล้ว ผลการเปลี่ยนแปลงนั้นจะต้องถูกบันทึกอย่างถาวรลงในสื่อบันทึกข้อมูล (Hard Disk) แม้หลังจากนั้นเพียงเสี้ยววินาที ระบบจะไฟดับ ไฟไหม้ หรือเครื่องพัง ข้อมูลที่ COMMIT ไปแล้วจะต้องไม่สูญหายไปไหนเด็ดขาด

วงจรสถานะของ Transaction (Transaction States)
--------------------------------------------------------------------------------
Transaction ประกอบด้วยสถานะการทำงานดังนี้:
1. Active: สถานะเริ่มต้น กำลังประมวลผลคำสั่งทีละบรรทัด
2. Partially Committed: ทำคำสั่งสุดท้ายใน RAM เสร็จแล้ว แต่ยังไม่ได้บันทึกเสร็จสมบูรณ์ลงดิสก์
3. Committed: บันทึกข้อมูลลงดิสก์ถาวรเสร็จสมบูรณ์แล้ว
4. Failed: เกิดข้อผิดพลาด ไม่สามารถประมวลผลต่อได้
5. Aborted: ถูกย้อนกลับ (Rollback) ข้อมูลคืนสู่สถานะเดิม และสิ้นสุดการทำงาน (Terminated)

ตัวอย่างในชีวิตประจำวัน เช่น การไปซื้อของที่ซูเปอร์มาร์เก็ต:
- แคชเชียร์เริ่มสแกนบาร์โค้ดสินค้าทีละชิ้น = Active State
- สแกนสินค้าครบทุกชิ้น คิดยอดรวมเงินออกมา = Partially Committed State
- คุณยื่นเงินสดหรือจ่ายบัตรเครดิตสำเร็จ ออกใบเสร็จ = Committed State
- แต่ถ้าแคชเชียร์กำลังสแกนอยู่ แล้วคุณบอกขอยกเลิก ไม่เอาของแล้ว หรือบัตรเครดิตรูดไม่ผ่าน = เกิด Abort / Failed State ยอดที่สแกนไว้ต้องถูกยกเลิก ไม่ตัดสต็อกสินค้า

การควบคุมสภาวะการทำงานพร้อมกัน (Concurrency Control)
--------------------------------------------------------------------------------
หากไม่มีระบบควบคุม เมื่อมี Transaction เข้ามาอ่านและเขียนข้อมูลชุดเดียวกันพร้อมกัน จะเกิด 3 ปัญหาใหญ่:

1. Lost Update Problem (ปัญหาการอัปเดตสูญหาย):
   ตัวอย่างเช่น บัญชีมีเงิน 1,000 บาท
   - Transaction A อ่านเงินได้ 1,000 บาท
   - Transaction B ก็เข้ามาอ่านเงินได้ 1,000 บาทเช่นกัน
   - A ถอนเงิน 500 บาท อัปเดตเงินเหลือ 500 บาท
   - แต่ B ซึ่งอ่านยอด 1,000 ไปก่อนหน้า ถอนเงิน 200 บาท แล้วอัปเดตยอดเงินทับกลายเป็น 800 บาท
   - ผลคือ ยอดที่ A ถอน 500 บาทสูญหายไปจากระบบ กลายเป็นธนาคารขาดทุน

2. Uncommitted Dependency / Dirty Read (ปัญหาการอ่านข้อมูลที่ยังไม่ยืนยัน):
   ตัวอย่างเช่น Transaction B ฝากเงิน 5,000 บาท แต่ยังไม่ได้ COMMIT
   Transaction A เข้ามาอ่านยอดเงินนั้นไปใช้ แต่จู่ๆ Transaction B เกิด Error แล้ว ROLLBACK ยกเลิกรายการ
   ผลคือ Transaction A ได้ข้อมูลที่เป็น 'ขยะ' (Dirty Data) ที่ไม่มีอยู่จริงไปประมวลผล

3. Inconsistent Analysis Problem (ปัญหาการวิเคราะห์ข้อมูลที่ไม่สอดคล้องกัน):
   ตัวอย่างเช่น มี 3 บัญชี: บัญชี 1 มี 40 บาท, บัญชี 2 มี 50 บาท, บัญชี 3 มี 30 บาท รวมเป็น 120 บาท
   Transaction A กำลังคำนวณหายอดรวม อ่านบัญชี 1 ได้ 40 บาท อ่านบัญชี 2 ได้ 50 บาท (รวมเป็น 90)
   ขณะนั้น Transaction B เข้ามาโอนเงิน 10 บาท จากบัญชี 3 ไปยังบัญชี 1 ทำให้บัญชี 3 เหลือ 20 และบัญชี 1 กลายเป็น 50 บาท แล้ว B COMMIT ไป
   พอ Transaction A มาอ่านบัญชี 3 ได้ยอดใหม่คือ 20 บาท นำมารวมกับ 90 บาทเดิม ได้ผลรวมเป็น 110 บาท ทั้งที่เงินในระบบมี 120 บาท ยอดเงินจึงหายไป 10 บาทเพราะข้อมูลไม่สอดคล้องกัน

การแก้ปัญหาด้วยกลไกการล็อก (Locking Mechanism & Lock Matrix)
--------------------------------------------------------------------------------
เราแก้ปัญหาด้วยการล็อกข้อมูล (Locking) ซึ่งมี 2 ชนิดหลัก:
1. Exclusive Lock (X-Lock / Write Lock):
   ใช้สำหรับการแก้ไขข้อมูล (INSERT, UPDATE, DELETE)
   ใครถือ X-Lock อยู่ คนอื่นจะเข้ามาขออ่าน (S) หรือขอเขียน (X) ไม่ได้เลยเด็ดขาด ต้องรอ (Wait)
2. Shared Lock (S-Lock / Read Lock):
   ใช้สำหรับการอ่านข้อมูลอย่างเดียว (SELECT / Query)
   อนุญาตให้หลาย Transaction ถือ S-Lock พร้อมกันได้ เพื่ออ่านข้อมูลร่วมกัน

ตาราง Lock Compatibility Matrix:
                 Lock ที่ถืออยู่เดิม:
Lock ที่ขอเข้ามา:     S (Shared)       X (Exclusive)
----------------------------------------------------
S (Shared)           YES (อนุญาต)     NO (ปฏิเสธ/รอ)
X (Exclusive)        NO (ปฏิเสธ/รอ)   NO (ปฏิเสธ/รอ)

สรุป: มีเพียงช่อง S และ S ช่องเดียวเท่านั้นที่ตอบ YES นอกนั้นเป็น NO ทั้งสิ้น!

กฎ Two-Phase Locking (2PL):
- Phase 1 (Growing Phase): ขอ Lock ได้เรื่อยๆ ห้ามปลด Lock
- Phase 2 (Shrinking Phase): ปลด Lock ได้เรื่อยๆ ห้ามขอ Lock เพิ่ม
หากเกิด Deadlock (การรอคอยซึ่งกันและกันจนระบบหยุดนิ่ง) DBMS จะต้องเลือก Victim 1 รายการเพื่อ Rollback

การกู้คืนระบบและความเสียหาย (System Failure & Recovery)
--------------------------------------------------------------------------------
ความล้มเหลวมี 2 ระดับ:
1. Media Failure (Hard Crash): ฮาร์ดดิสก์พัง หัวอ่านขูดจานแม่เหล็ก ข้อมูลในดิสก์เสียหาย -> ต้องใช้การสำรองข้อมูล (Backup) จากเทป/เซิร์ฟเวอร์สำรองมา Restore
2. System Failure (Soft Crash): ไฟฟ้าดับ ชิปประมวลผลค้าง RAM ดับ แต่ข้อมูลใน Hard Disk ยังอยู่ดี -> กู้คืนโดยอาศัย Log File

หลักการ Write-Ahead Logging (WAL) และการกู้คืน:
- ทุกคำสั่งของ Transaction ต้องถูกบันทึกเขียนต่อท้ายใน Log File บนดิสก์ก่อนเสมอ
- เมื่อระบบล่มแล้วเปิดขึ้นมาใหม่ DBMS จะตรวจเช็ค Log File:
  - Transaction ใดที่มีคำสั่ง COMMIT อยู่ใน Log -> แปลว่าผู้ใช้ทำสำเร็จแล้ว ให้สั่ง 'REDO' (ทำซ้ำเพื่อยืนยันข้อมูลลงในฐานข้อมูล)
  - Transaction ใดที่มีแต่ START แต่ยังไม่เจอ COMMIT -> แปลว่าค้างอยู่ตอนระบบล่ม ให้สั่ง 'UNDO / ROLLBACK' (ยกเลิกเพื่อคืนค่าเดิม ป้องกันข้อมูลผิดพลาด)
- Checkpoint: เป็นจุดที่ระบบสั่งบันทึกข้อมูลจาก Buffer ทั้งหมดลง Disk เพื่อให้ไม่ต้องย้อนกลับไปอ่าน Log ไกลเกินไป"
